The last row is the deep one: it is not a path disagreement, it is two different delivery architectures for the same Python. Standalone T03 and Wheel T4 are the *same* `git mv` to *different* destinations, and Visualizer T2.3 edits a file both of the others have already moved or gutted.

**Consequence:** every `verification` field in all three specs is path-keyed. Run any two specs in either order and roughly a third of the verification commands become unsatisfiable — not failing, *unrunnable*, which is the failure mode that reads as green in a script.

**A fourth consumer no spec lists** (`[ran]` grep for `praxis_bootstrap`): `praxis/web-client/e2e/specs/jupyterlite-bootstrap.spec.ts`. It breaks under all three layouts.

Deltas from each spec, all mechanical:
- **Wheel spec** unchanged except manifest lands in `web-repl/dist/assets/wheels/` instead of `praxis/web-client/src/assets/wheels/`. R4/R5/R6/R8 greps re-scope; the semantics survive intact.
- **Standalone spec** loses T03's mass move (Phase 3 already did it) and its `overlay/assets/{shims,python}/` disappear — the shims ship *inside the wheel* instead of as loose fetched files. This is a real change to standalone's R12 (it becomes "there is exactly one wheel, not one fetch location") and it **kills the fast edit→reload loop** the wheel spec's own pre-mortem calls its #1 failure risk. That cost is priced in §7 (wheel spec T16 measures it; re-litigation is a live condition).
- **Visualizer spec** moves `praxis/viz/` into `praxis-browser/praxis_browser/viz/` (ships in the wheel, no new fetch entries — its T2.3 becomes a no-op) and the vendored renderer to `web-repl/vendor-visualizer/`. **Alternative, if the edit→reload loop is judged decisive:** keep loose-file fetch for the four shims + `web_bridge.py` (standalone's shape), ship only PLR as a wheel, and reduce the wheel spec to manifest-indirection + loud-boot over the existing fetch loop. The wheel spec *names this as its own runner-up design* and calls it "strictly smaller." This is a genuine fork, not a formality.

**The three test-design traps** (each produces a silently-vacuous green; all three were caught only by execution):
1. `page.route()` **does not intercept Web Worker requests.** The offline gate must use chromium launch args `--host-resolver-rules="MAP cdn.jsdelivr.net 127.0.0.1:1"` (+ `pypi.org`, `files.pythonhosted.org`). A `route()`-based version passes vacuously.

**All three device APIs are present in headless Chromium — in a secure context.** Served over `http://127.0.0.1:<port>`:

```
isSecureContext        = True
navigator.serial       = True
navigator.usb          = True
navigator.hid          = True
typeof Worker          = function
crossOriginIsolated    = False        # expected: no COOP/COEP headers on a bare http.server
```

**Do not read this off an `about:blank` page.** The same probe on `about:blank` reports `navigator.serial = False`, because `about:blank` is not a secure context. That is a secure-context artifact, NOT a headless limitation, and mistaking one for the other would wrongly downgrade Phase 2's headless scope. Every browser probe must therefore be served over `http://127.0.0.1` (or `localhost`), never `about:blank` or a `file://` URL.

**Still unverified from that warning list:** `cdn.jsdelivr.net` reachability from the sandbox. Pyodide fetches from it unless vendored, so S-A/S-B/S-D must either run with the sandbox disabled or use a vendored Pyodide tarball (standalone `scripts/fetch_pyodide.py`). Resolve at Phase 2 entry.
